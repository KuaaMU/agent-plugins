# 检查点与漂移响应

## 检查点是什么

检查点是“第一次能在真实证据上验证某个主张”的时机，不是任务清单的章节。3-5 个就够，每个检查点必须能回答：做完后我能拿出什么证据证明这件事成立？

## 通用检查点类型（按需挑选）

- 环境冒烟：目标环境能运行最小程序/命令，拿到版本号或健康输出。
- 最小端到端：从输入到输出走通最短路径，哪怕结果是错的。
- 核心正确性：关键算法/接口在真实或最接近真实的数据上得到正确结果。
- 回归对比：新实现与旧实现/基线在同一数据集上比较，记录差异。
- 验收交付：按当前任务书逐条核对验收标准，证据存档。

## 出口证据模板

每个检查点记录：

- 检查点：一句话。
- 证据：可复现命令 + 关键输出 + 日期 + 环境。
- 判定：通过/不通过/部分通过。
- 未解决风险：一句话。

失败也是证据：把失败命令、报错、尝试过的假设写下来，下一轮从证据出发而不是记忆出发。

## 漂移响应表

| 情况 | 动作 |
| --- | --- |
| 任务书/验收标准变化 | 更新 TRUTH.md 与 PLAN.md，向用户确认后继续 |
| 验收标准互相矛盾 | 写入 STATE.md，按证据最强版本继续，同时请求确认 |
| 事实来源过期 | 重新核对并更新核对时间，过期事实不做关键决策 |
| 平台/依赖更新 | 先最小冒烟验证，通过后再迁移 |
| 同一问题 3 个思路失败 | 停止攻坚，换路径或问用户，写 BLOCKED 记录 |
| 用户给了新背景/链接 | 先蒸馏进 TRUTH.md 再决定是否改变当前检查点 |

## 示例检查点表（通用）

| # | 检查点 | 出口证据 | 通过标准 |
| --- | --- | --- | --- |
| 1 | 环境冒烟 | 最小程序在目标机运行输出版本号 | 输出与任务书一致 |
| 2 | 最小端到端 | 一条输入走完主流程 | 无崩溃，结果可解释 |
| 3 | 核心正确性 | 关键用例结果 | 与期望/基线一致 |
| 4 | 回归 | 新旧实现对比数据 | 性能与准确率达到阈值 |
| 5 | 验收 | 验收标准逐条核对记录 | 全部通过，无 P0/P1 |
