## 操作面板（先读这一节，再读下面的原则）

**输入**：算子名 + host 侧路由源码路径 + 硬件型号/工具链版本 + （可选）不达标的形状段。
**输出**：`<算子>_FAMILY_AUDIT.md`，含 §1 的家族审计表（每行必须有 `假设/已验证`）、
§3 的容量推导、以及"该新开家族 vs 继续调优"的判定。

**编号工作流**

```
1. 读 host 侧全部路由分支，逐条抄成 §1 的表（形状段 / 由谁算 / 为什么 / 状态）
2. 对每一行的"为什么"三联判：
      写得出容量或位宽推导      → 标【已验证】，附推导
      写的是"一直如此/继承来的"  → 标【假设】，进未验证清单
      写的是特例（n==31 && …）   → 标【红旗】：这张表是对着用例调的
3. 抽该算子用到的硬件常量（向量宽度 / 线程组宽度 / 片上缓存容量）—— 从 platform 接口取，不硬编码
4. 检查每个家族的容量是否可推导（§3 模板）；把 static_assert 补上
5. 对不达标的形状段做 §4 三条检验（忙管 >95% / 已达算法下界 / 结构项全排除）
      三条全中 → 停微杠杆，转"新家族"或"外部对标"
6. 若某形状段的尺寸与现有家族不匹配（如"为整尺寸定尺寸的核去算约一半尺寸的形状"）
      → 这是新开家族的信号，不是调参的信号
7. 落盘 FAMILY_AUDIT.md，跑下面的自检
```

**检查点（必须停下等确认）**

| 时点 | 确认什么 |
|---|---|
| 抄表后 | 表里是否有一行的"为什么"**答不上来**——那就是本次的待验证假设 |
| 定切点前 | 切点是否来自硬件常量；若来自"能通过测试的最大值"⇒ **停，重算** |
| 决定新开家族前 | 是否已有邻居/自己 A/B 的存在性证明（否则先做 `upstream-recon`） |
| 改布局前 | `static_assert` 是否已就位（没它就等于没有不变量） |

**怎么算做完了**（可机械判定）

```
test -f *_FAMILY_AUDIT.md                            # 落盘
grep -c '假设\|已验证\|红旗' *_FAMILY_AUDIT.md        # 每行都标了状态
grep -c 'static_assert' <算子源码>                    # 容量不变量已写成编译期检查
grep -cE 'n ?== ?[0-9]+ *&&|batchSize ?>=' <算子源码>  # 手调特例计数（越少越好）
```

# 形状 → 执行家族：设计与推导

> **本 skill 补的是 38 个现有 skill 里的一个结构性空缺**：
> `<切分设计 skill>` 与 `<SIMT 切分设计 skill>` 都**假定执行模型已经选好**，
> 它们教你"选定 SIMT 之后怎么切核"或"选定 SIMD 之后怎么切片上缓存"，
> **但没有一个回答"这个形状该由哪套模型算，以及为什么"**。
> 真实事故：一个算子的小尺寸段走了通用线程式路径，两年无人问过为什么；
> 相邻形状段走了向量路径，实测 **比线程式路径快数倍**——
> 这份证据就在自己的实验记录里，却被读反了主语，于是整条路由被押在了错误的模型上。

---

## 0. 三条硬规则

> **硬规则 0.1：继承来的路由是假设，不是给定条件。**
> 对分档表里**每一行**问一次：**"这个形状为什么由它来算？"**
> 答不上来的，标为**未验证假设**，并给出证伪它的最小实验。

> **硬规则 0.2：分档必须可推导。**
> 阈值应由**容量 / 位宽 / 连续尺寸范围**算出，并写成 `static_assert` 让编译器守；
> 不得是手调常数表加特例。**手调表是技术债**——它让所有人都不敢动架构，
> 于是所有努力自然流向"在旧路径上调优"。见 §3。

> **硬规则 0.3：「这条路径没有余量」≠「这个问题没有余量」。**
> 一条路径测到忙管 >95%、算术已在下界、结构项全部排除之后，
> 允许的下一步**只有两个**：**换表述**（新家族）或**对标外部**。
> **继续在该路径上做微杠杆是禁止项，不是"再试一次"。**

## 1. 先做一次"家族审计"（接手时的第一个动作）

把现有 host 侧路由读出来，列成这张表，**每一行都必须填满**：

| 形状段 | 当前由谁算 | 为什么 | 状态 | 证据 |
|---|---|---|---|---|
| <小尺寸段> | `<kernel>` | ? | **假设/已验证** | |
| <中尺寸段> | | | | |
| … | | | | |

**"为什么"这一栏的判别法**：
- 写得出**容量/位宽推导**（"因为一个向量寄存器能装 64 个浮点，超过就要跨寄存器"）⇒ **已验证**
- 写的是"一直如此 / 继承来的 / 历史沿用" ⇒ **假设**，进 §1 的未验证清单
- 写的是**特例**（`n == <定值> && batchSize >= <定值>`、`n == <定值> || n == <定值> || n == <定值>`）⇒ **红旗**，
  说明这张表是**对着测试用例调的**，不是对着硬件算的

> **反例（真实的）**：某算子的路由写着
> `(n == <定值> && batchSize >= <定值>) ? <定值>U : (((n >= <定值> && n <= <定值>) && perCoreBatch > <定值>U) ? <定值>U : …)`
> ——**逐字对着特定 n 和特定 batch 调**。而同期一份通过验收的实现的同一张表写的是
> 「一个家族切点 = 线程组宽度」「另一个 = 向量宽度」，
> **两个常量都直接来自硬件**。

## 2. 执行模型选择：先看形状，再看容量

| 模型 | 什么时候是它 | 判据（**逐条检验，不要凭感觉**） |
|---|---|---|
| **SIMT**（线程式） | 逐元素、条件分支多、不规则访问；少量数据、大量分支 | 每线程的算术能掩盖访存延迟；**分支发散可控** |
| **SIMD**（向量寄存器） | 规则形状、可整块向量化、**车道能被填满** | 形状能整除/接近向量宽度；**lane 利用率**是首要判据 |
| **矩阵/tensor 单元** | 稠密矩阵乘、维度够大能摊薄启动与搬运 | 单个 tile 的 cube 占用率；小形状启动开销占主导 |
| **混合** | 主体规则 + 边角不规则 | 拆开的代价 < 收益 |

> **判据里最容易错的是 lane 利用率。**
> 一个尺寸约为家族尺寸一半的形状，放进一个按整尺寸定尺寸的向量核里，
> 会在**半空的平面上做满宽运算**——不是因为向量模型不适合小 n，
> 而是因为**这个向量核不是为这个形状定尺寸的**。
> ⇒ **模型的适用性和内核的尺寸是两件事，分开判。**

> **反例（真实的）**：某算子的**小尺寸段**走线程式模型，**相邻的稍大尺寸段**走向量模型。
> 同一条带的相邻段，两种执行模型，跑出 **数倍差距**。
> 而同期一份通过的实现把**整段小尺寸交给了向量家族**。
> ⇒ 那条分界线**不是硬件决定的**，是历史决定的。

## 3. 容量推导：让阈值算出来，让编译器守

**模板**（照抄这个形状）：

```cpp
// ① 硬件常量：从 platform 接口取，不要硬编码
constexpr uint32_t kVectorWidth = kVectorWidthFromPlatform();  // 向量宽度（勿写死）
constexpr uint32_t kThreadsPerGroup = kThreadsPerGroupFromPlatform();
// ② 家族切点：由硬件常量导出，不是拍的
constexpr uint32_t kPackedMaxRows = kThreadsPerGroup;   // 一个线程组一行
constexpr uint32_t kVectorRows    = kVectorWidth;       // 一个向量寄存器一行
// ③ 预算：由容量推导
constexpr uint64_t kDynamicBytes = /* 布局算术 */ <本布局推导出的字节数>;
constexpr uint64_t kTotalBytes   = /* 片上实际可用 */;
constexpr uint64_t kStaticReserve = /* 预留 */;
static_assert(kDynamicBytes + kStaticReserve <= kTotalBytes, "片上预算超了");
static_assert(kPackedMaxRows <= kThreadsPerGroup, "...");
```

**驻留上限不要查表，算出来**：

```cpp
constexpr uint32_t MaxResidentSize() {
    uint32_t n = kVectorRows + 1;        // 从第一个可能驻留的尺寸起
    while (IsResidentSupported(n)) ++n;  // 真的循环算，而不是写死一个数
    return n;
}
```

> **这样做的收益不是"优雅"，是"可改"**：改布局时阈值自动跟着变，加一个家族很便宜。
> **代价对照**：手调表下一次布局改动要重调整张表 ⇒ 没人敢动 ⇒ 架构冻结。

**诚实边界**：预算常量在工程上常是"推导 + 标定"混合（一部分来自实测标定）。
这可以接受，但**必须区分**：**切点来自硬件常量（可推导）**，
**预算来自标定（要写清是标定值）**。把标定值伪装成推导值，就是在制造手调表。

## 4. 决策：在旧路径上调优，还是新开一个家族？

> ### §4.0 —— **先看这一条**：尺寸不匹配 ⇒ **触发一次"错配核算"**（不是直接下结论）
>
> **触发条件（可机械检查）**：**绑定该形状的那个尺寸参数**为 `M`
> （列跨距固定、行平面固定高度、片上预算固定、线程数固定），而目标形状 `n < M/2`。
>
> **⇒ 必须做一次核算，两项：**
>
> **(a) 被浪费的资源，在不在绑定管上？**
> 若浪费的是**掩码 lane / 未用预算**，而**绑定管的占用率已接近 100%**，
> 则**这个浪费是免费的**。
> *实测（可复现的一课）*：一个按整尺寸定尺寸的家族被拿去算约一半尺寸的形状，
> 浪费了约三分之一的 lane-slot；专门做了一轮"消除该浪费"的实验，
> **预期两位数百分比的收益，实测接近零**——**浪费确实免费**。
> ⇒ **错配不是杠杆，回落去做 §4 的三条。**
>
> **(b) 这个用例是不是固定开销主导？**
> 若时间花在启动 / 搬运 / 准备上（小 `n` **且** 小 `batch` 的延迟型用例），
> **先解决固定开销**——重定尺寸不解决这个问题。
>
> **两项都指向"错配确实在花钱" ⇒ 判"新开家族"。否则回落到 §4 的三条。**
>
> **⚠️ 动作是「新开一个为该形状定尺寸的家族」，不是「重路由到已有家族」。**
> 实测反例：把一个小尺寸段**重路由**到一个"按 2 倍尺寸定尺寸"的核，
> **正确性直接失败**——那个核的列跨距与元数据布局是按大尺寸定的，
> 它的切分点是**结构性的**，不是路由选择。**重路由 ≠ 新家族。**
>
> **为什么要有这一条（以及为什么它必须是"核算"而不是"结论"）**：
> 下面的三条是「当前路径**已经完美**」的最强前提，而"该新开家族"的条件**可能比它弱得多**
> ——若把三条当成换家族的**唯一**入口，就会得到反直觉的结果：
> **当路径里还有一个"看起来可以优化"的结构项时（例如 lane 利用率偏低），
> 规则会判"未耗尽 ⇒ 继续调优"——而这正是把整场攻坚锁死在错误架构里的方式。**
> 但反过来，"尺寸不匹配"也**不能**直接推出"该换"——**上文的 (a) 就是"看起来可怕、实测为零"的那一类。**
>
> **一句话（两半都要）**：
> **「有优化空间」不等于「该在这里优化」；但「空间」是不是真的在花钱，要先测，不能从尺寸推。**

**以下三条适用于"尺寸匹配、或错配核算判定为免费"的情形。满足全部三条 ⇒ 禁止微杠杆，必须新开家族或对标：**

1. **忙管 > 95%**（如 `向量管占用率 ≥ 0.95`）；**且**
2. **算术已达算法下界**（**写下界**，不是"看起来不多"：LU 的因子分解是 `n³/3`）；**且**
3. **结构项全部排除**（访存冲突、lane 利用率、同步、竞争、调度，逐项有实测或推导）

> **真实代价**：某战役三条早已**同时成立且被正确测出**，结论却写成了
> "没有杠杆了 ⇒ 大概是形成层极限"，此后又做了 **4 轮微杠杆实验，全部被否**。
> 正确推论是"**这条路径没有余量 ⇒ 该换形状**"。
> **注意措辞：禁止的是"微杠杆"，不是"实验"**——照做就是**去写一个为该形状定尺寸的新内核**。

**新家族的形状从哪来**（按可得性排序，见 `long-horizon-attack` §6）：

1. **同仓 / 同上游的兄弟算子**里，同形状段已经用另一种安排通过的——**它的存在性证明就是证据**；
2. **相邻形状段你自己的 A/B**（尤其"邻带用了另一种表述"那种）；
3. 上游参考库 / 文档 / 硬件白皮书；
4. 竞品——**通常在你需要它时不存在，不得放入关键路径**。

> **一句判据**：**"同族算子在同一硬件上用另一种安排通过了"**，
> 这不是传闻，是**证据**。要否掉它必须给**机制**（它为什么在这里不成立），
> 不能只说"表述不同"。

## 5. 反模式清单

| 反模式 | 为什么危险 | 改成 |
|---|---|---|
| 手调常数表 + 特例 | 冻结架构，努力流向微杠杆 | `constexpr` 推导 + `static_assert` |
| 阈值写成"能通过测试的最大值" | 对着用例调，不是对着硬件算 | 写容量推导 |
| 单文件几千行、家族全挤在里面 | 改一处动全身，没人敢动 | 薄启动器 + 每家族一个 TU + 共享库 |
| env 门控探针堆在主干上 | 新探针容易插到不可达位置，且主干不可读 | 探针进独立 TU；实验必须 commit |
| 一个家族覆盖过宽的 n 段 | 大 n 的形状把尺寸定死，小 n 在半空平面上做满宽运算 | 按形状切成连续段，每段一个家族 |
| "先调优，架构以后再说" | 调优的收益会被架构错误整个吃掉 | 先做 §1 家族审计，再动性能 |

## 6. 最小工作流

```
1. 读 host 侧路由，填 §1 家族审计表；每一行标注 假设/已验证
2. 对每个"假设"行问：这个形状为什么由它算？→ 进未验证假设清单
3. 检查每个家族的容量是否可推导（§3）；标出所有手调特例
4. 对不达标形状段做 §4 三条检验：
   全中 ⇒ 停微杠杆，转 新家族 / 对标
5. 新家族的设计：先算容量预算，写成 static_assert，再写代码
6. 若形状段与现有家族尺寸不匹配（如"为整尺寸定尺寸的核去算约一半尺寸的形状"），
   ⇒ 这是"新开家族"的信号，不是"调参"的信号
```

> **一句话**：**分档表是这个算子的架构声明。**
> 如果它是手调的，那这个算子就没有架构，只有一堆对着测试调出来的数；
> 而在没有架构的地方，所有优化努力都会流向"把错的路径调快"。
